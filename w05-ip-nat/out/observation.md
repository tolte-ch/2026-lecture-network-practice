## Task 1 — 서브넷과 Longest-Prefix Match

### 기본 검증 결과

`python3 task1_forward.py --verify`를 실행한 결과, 네 개의 네트워크 범위 계산과 여섯 개의 forwarding lookup이 모두 성공하여 `10/10 ok`가 출력되었다. `/24`, `/8`, `/20`, `/26` 네트워크의 첫 번째 usable 주소, 마지막 usable 주소, broadcast 주소가 예상 결과와 일치했다. 또한 각 목적지 주소에 대해 가장 적절한 next hop이 선택되는 것도 확인했다.

### /31과 /32 처리

`/31`은 RFC 3021의 point-to-point 링크 방식을 적용하여 두 주소를 모두 사용할 수 있는 주소로 처리했다. `192.0.2.0/31`을 실험한 결과 첫 번째 주소는 `192.0.2.0`, 마지막 주소는 `192.0.2.1`로 반환되었다. `/32`는 하나의 호스트만 나타내는 host route로 해석하여 `192.0.2.7`을 첫 번째와 마지막 주소로 동일하게 반환했다. 두 경우 모두 일반적인 의미의 별도 broadcast 주소는 없으며, 함수의 반환 형식을 유지하기 위해 주소 블록의 마지막 값을 세 번째 값으로 반환했다.

### 잘못된 CIDR 입력 검사

`163.152.6.5/24`는 `/24` 네트워크의 host bit가 설정된 주소이므로 `ValueError`로 거부되었다. 또한 IPv4 prefix의 범위 `0~32`를 벗어난 `10.0.0.0/33`과, octet의 허용 범위 `0~255`를 벗어난 `300.0.0.0/8`도 각각 오류로 처리되었다. 이때 출력된 traceback은 프로그램이 실패한 것이 아니라 유효하지 않은 입력을 의도한 대로 검출했다는 의미이다.

### Longest-prefix match

`10.20.30.70`은 `10.0.0.0/8`, `10.20.0.0/16`, `10.20.30.0/24`, `10.20.30.64/26`에 모두 포함되었다. 이 중 prefix 길이가 가장 긴 `/26`이 가장 구체적인 경로이므로 next hop으로 `rack`이 선택되었다. 반면 `8.8.8.8`은 등록된 구체적인 네트워크에 포함되지 않으므로 모든 주소와 일치하는 기본 경로 `0.0.0.0/0`을 통해 `default`가 반환되었다.

### 동일한 prefix 길이의 경로

동일한 네트워크와 prefix 길이에 서로 다른 next hop이 등록되면 어느 경로를 선택해야 하는지 모호해질 수 있다. 이를 방지하기 위해 이미 등록된 `10.0.0.0/8`을 다시 추가하면 `ValueError: duplicate route`를 발생시키도록 구현했다. 따라서 등록 순서에 따라 next hop이 임의로 결정되지 않으며, 중복 경로를 잘못 구성된 forwarding table로 판단하여 명시적으로 거부한다.

## Task 2 — 주소, NAT, DHCP 관찰

WSL에서 측정한 private 주소는 `172.24.204.95/20`이고 외부에서 보인 public 주소는 `123.215.41.197`이었다. 두 주소가 다르므로 최소 한 단계의
NAT가 존재하지만, 정확한 NAT 계층 수를 알려면 Windows의 물리적 인터페이스 주소와 공유기의 WAN 주소를 추가로 비교해야 한다.

카페 Wi-Fi와 집 Wi-Fi에서 WSL의 private 주소는 모두 `172.24.204.95/20`, gateway는 `172.24.192.1`로 동일했다. 물리적인 네트워크가 변경되어도 WSL이 동일한 가상 NAT subnet을 유지했기 때문이다.

Public IP는 카페 Wi-Fi의 `123.215.41.197`에서 집 Wi-Fi의 `219.254.143.209`로 변경되었다. 이는 실제 인터넷 회선과 NAT 출구가 달라졌음을 보여준다. Private 주소와 public 주소가 다르므로 최소 한 단계의 NAT가 존재하며, WSL과 공유기 구조를 고려하면 두 단계 이상일 가능성이 있다.

실시간 캡처에서는 전체 DORA를 얻지 못해 Task 2의 Path B에 따라 공식 DHCP trace를 분석했다. Discover는 아직 IP가 없는 클라이언트가 전송하므로 source가 `0.0.0.0`, destination이 `255.255.255.255`였다.

DHCP 서버 `192.168.86.1`은 클라이언트에 `192.168.86.65`를 제안하고 ACK를 통해 할당을 승인했다. Lease time은 86,400초인 24시간이었으며, 클라이언트는 일반적으로 그 절반인 12시간 후부터 갱신을 시도한다.

Discover는 서버와 자신의 주소를 알지 못하므로 broadcast로 전송되었지만, ACK는 `192.168.86.1`에서 할당 주소 `192.168.86.65`로 unicast되었다. 이 캡처에서는 broadcast flag가 0이었기 때문에 서버가 클라이언트 주소로 직접 ACK를 전송할 수 있었다.

## Task 3 — 빠른 Longest-Prefix Match

### 구현한 자료구조

경로를 prefix 길이별 dictionary에 나누어 저장하고, 실제로 사용 중인 prefix 길이를 긴 순서대로 검사하도록 구현했다. 각 길이의 mask를 주소에 적용한 뒤 계산된 network가 dictionary에 존재하면 즉시 next hop을 반환하므로 longest-prefix match가 보장된다.

이 구조는 경로마다 dictionary entry가 하나씩 필요하므로 경로 저장에 `O(N)`의 메모리를 사용한다. 이와 함께 33개의 prefix별 dictionary와 mask, 사용 중인 prefix 길이 목록을 저장하지만, 이는 IPv4에서 고정된 크기이다.

### 정확성 및 성능 결과

`bench.py`가 생성한 5,000개의 prefix와 20,000개의 조회를 대상으로 실험했다. 마지막 측정에서 LinearTable의 lookup 시간은 29.460초였고, 새로운 YourTable의 lookup 시간은 0.016초였다. 처리량은 초당 679회에서 1,221,858회로 증가하여 1,799.8배의 성능 향상을 기록했다.

모든 실험에서 `wrong 0`과 `every answer matches`가 출력되었으므로 20,000개의 조회 결과가 LinearTable과 모두 동일했다. 세 번의 성능 향상은 각각 1,126.4배, 1,937.5배, 1,799.8배였으며, 모두 1,000배 이상이므로 Task 3의 `strong` 기준을 충족했다.

### 조회 시간복잡도

LinearTable은 조회할 때 5,000개의 경로를 모두 검사하므로 lookup 시간이 전체 경로 수 `N`에 비례하는 `O(N)`이다. 새로운 구조는 전체 경로를 순회하지 않고 실제로 사용 중인 prefix 길이만 검사하므로 조회 작업량은 prefix 길이 종류의 수 `K`에 비례하는 평균 `O(K)`이다.

IPv4의 prefix 길이는 `/0~32`까지 최대 33개뿐이고 이번 benchmark에서는 약 7종류만 사용되었다. 각 dictionary 조회는 평균 `O(1)`이므로 경로가 5,000개로 증가해도 lookup에서 검사하는 항목 수는 크게 증가하지 않는다.

### 소프트웨어와 하드웨어의 차이

하드웨어 라우터는 주소를 한 비트씩 따라가는 trie 구조를 사용하면 최대 32단계 안에 결과를 찾을 수 있고, 동작 시간이 예측 가능하며 파이프라인이나 병렬 회로로 구현하기 쉽다. 따라서 bit-walk 방식은 하드웨어 구현에 적합하다.

반면 Python에서는 trie의 각 노드를 한 단계씩 방문하면 Python 객체 접근과 반복문 비용이 발생한다. Prefix 길이별 hash table은 최적화된 dictionary 연산을 사용하고 이번 실험에서는 약 7개의 길이만 확인하면 되므로, Python 환경에서는 bit-walk 방식보다 더 빠른 결과를 얻을 수 있다.
